## 本阶段发现并修复的问题

### 问题：Open WebUI Ollama 代理与 RAGFlow LiteLLM 调用不兼容

现象：

```text
INVALID_REQUEST - litellm.APIConnectionError: Ollama_chatException
Input should be a valid dictionary
```

排查结论：

- 手动请求 `http://153.101.206.98:50028/ollama/api/chat` 可以正常调用 `deepseek-r1:70b`。
- RAGFlow 原先通过 LiteLLM 的 `ollama_chat/` provider 调用 Ollama。
- 在当前 Open WebUI 代理环境下，请求体被 Open WebUI 判定为字符串，而不是 JSON 字典。
- Embedding 解析可用，但 Chat 生成失败，说明问题集中在 chat provider 请求方式。

处理：

- 新增 `OllamaChat` 原生实现。
- 使用 `ollama.AsyncClient` 调用 chat。
- 支持 Bearer Header，兼容 Open WebUI `/ollama` 代理。
- 让 `ChatModel["Ollama"]` 指向原生 `OllamaChat`，覆盖 LiteLLM 的 Ollama 映射。

验证：

```text
ChatModel["Ollama"].__name__ = OllamaChat
```

手动代理验证：

```text
POST /ollama/api/chat -> 200
POST /ollama/api/embed -> 200
POST /ollama/api/embeddings -> 200
```

## 当前限制与下一阶段优化点

1. `deepseek-r1:70b` 单次回答耗时较长，本阶段三次回答耗时约 215 秒、255 秒、239 秒。
2. 开启自动引用插入时，部分文本会触发 `bge-m3` 二次编码 NaN 问题，因此当前 Dialog 关闭了自动引用插入。
3. `deepseek-r1:70b` 偶尔会输出推理过程式表达，后续需要进一步优化系统提示词或切换更适合业务问答的非 reasoning 模型。
4. Q&A 文件已先按 General 方式稳定入库，后续可清洗 Excel 后再构建专门的 Q&A 知识库。
