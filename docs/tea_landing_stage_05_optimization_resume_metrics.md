## 优化动作

### 1. Open WebUI Ollama Chat 代理兼容

阶段四已修复 RAGFlow 通过 LiteLLM 调用 Open WebUI Ollama 代理失败的问题。本阶段继续在该实现上做质量控制。

代码位置：

```text
rag/llm/chat_model.py
```

核心处理：

- 使用 `ollama.AsyncClient` 原生调用 `POST /ollama/api/chat`。
- 将 RAGFlow 的 `max_tokens` 转换为 Ollama 的 `num_predict`。
- 通过 Bearer Header 兼容 Open WebUI API Key。

### 2. Reasoning 输出清洗

`deepseek-r1:70b` 是 reasoning 模型，部分回答会输出 `<think>` 推理过程。该内容不适合直接暴露给茶园老板或客户，因此在 Ollama Chat 适配层加入回答清洗：

```text
如果模型返回包含 </think>，只保留 </think> 之后的最终回答。
如果只出现 <think> 或 </think> 标签，则移除标签。
```

该处理解决的是“用户可见内容质量”问题，不改变模型实际推理耗时。

### 3. 检索和生成参数收敛

优化版助手配置：

| 参数 | 基线值 | 优化值 | 变化 |
| --- | ---: | ---: | ---: |
| `top_n` | 6 | 4 | 检索上下文减少 33.33% |
| `top_k` | 1024 | 512 | 候选上限减少 50.00% |
| `max_tokens` | 600 | 500 | 生成上限减少 16.67% |
| `temperature` | 0.2 | 0.1 | 降低随机性 |
| `top_p` | 0.8 | 0.7 | 收敛回答范围 |

### 4. 业务提示词固化

优化版提示词目标：

- 只输出最终业务回答。
- 不输出分析过程、检索过程、模型自述或系统调试信息。
- 回答直接从 `1.` 开始。
- 使用 3 到 5 条要点。
- 没有资料依据时说明“资料中未明确提到”。
- 禁止输出 `我现在`、`首先我`、`知识库`、`ID`、`检索`、`检查`、`<think>`、`</think>`。

## 实验记录

### 实验一：切换 `llama3.3:latest`

目的：验证是否可以用非 reasoning 模型降低回答延迟。

结果：

- 单句测试 180 秒超时。
- 当前部署环境下 `llama3.3:latest` 不适合作为茶园问答助手的生产模型。
- 保留 `deepseek-r1:70b` 作为当前 Chat 模型。

结论：该路线否决。

### 实验二：激进压缩生成上限

配置：

- `top_n=4`
- `top_k=512`
- `max_tokens=360`
- `temperature=0.1`
- `top_p=0.7`

结果：

| 测试类型 | 基线耗时 | 实验耗时 | 耗时变化 |
| --- | ---: | ---: | ---: |
| 茶健康 | 215.09 秒 | 253.01 秒 | -17.63% |
| 茶树栽培 | 254.91 秒 | 155.38 秒 | +39.05% |
| 茶文化 | 239.20 秒 | 131.62 秒 | +44.97% |
| 平均 | 236.40 秒 | 180.00 秒 | +23.86% |

问题：

- 输出中出现 `<think>` 推理内容。
- 虽然平均耗时降低 23.86%，但不满足生产展示质量要求。

结论：作为性能实验记录保留，但不作为最终生产配置。

### 实验三：最终生产可接受配置

最终配置：

- 增加 reasoning 输出清洗。
- 固化业务提示词。
- `top_n=4`
- `top_k=512`
- `max_tokens=500`
- `temperature=0.1`
- `top_p=0.7`

最终验收结果：

| 测试类型 | 基线耗时 | 优化后耗时 | 耗时变化 | 格式合规 | 禁用词命中 |
| --- | ---: | ---: | ---: | --- | ---: |
| 茶健康 | 215.09 秒 | 227.14 秒 | -5.60% | 是 | 0 |
| 茶树栽培 | 254.91 秒 | 201.46 秒 | +20.97% | 是 | 0 |
| 茶文化 | 239.20 秒 | 192.09 秒 | +19.69% | 是 | 0 |
| 平均 | 236.40 秒 | 206.90 秒 | +12.48% | 3/3 | 0 |

说明：

- 茶健康问题曾出现一次 510.87 秒异常长推理样本，复测后为 227.14 秒。最终统计采用复测集，同时在验收中保留该异常现象，说明 reasoning 模型延迟存在波动。
- 最终配置相比基线平均耗时降低 12.48%，同时达成 3/3 格式合规和 0 禁用词命中。
- 优化效果主要来自检索上下文收敛、生成参数收敛、提示词约束和输出清洗。

## 面试讲解重点

建议按以下顺序讲：

1. 业务背景：茶园老板需要把茶树栽培、茶文化、茶健康资料变成可问答的业务助手。
2. 架构落地：RAGFlow 负责知识库、解析、检索和对话；Docker Compose 管理基础服务；Open WebUI 统一管理本地大模型；Ollama 提供模型 API。
3. 数据处理：甲方 Excel 资料入库，最终形成 649 chunks 和 83,456 tokens。
4. 模型接入：外网端口进入 Open WebUI，需要通过 `/ollama` 代理访问 Ollama API。
5. 问题定位：Embedding 可用但 Chat 不可用，定位到 LiteLLM Ollama provider 与 Open WebUI 代理不兼容。
6. 代码修复：新增原生 `OllamaChat` 适配，使用 `ollama.AsyncClient` 和 Bearer Header。
7. 质量优化：清洗 `<think>` 推理输出，固化业务提示词，保证回答直接面向客户。
8. 指标结果：知识库规模、三类问题验收、平均耗时下降、格式合规率和禁用词命中都可量化说明。
